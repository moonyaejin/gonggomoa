# 기록 체계

## 왜 첫 주부터 기록하는가

자기소개서와 포트폴리오에서 힘을 갖는 문장은 이런 형태다.

> "LLM 추출 자동 승인률이 초기 58%에 그쳐, 실패 사례 40건을 분류한 결과 표 형태 공고에서 오류가 집중됨을 확인했습니다. 프롬프트에 표 구조 처리 지침을 추가해 3주 만에 89%로 개선했습니다."

이 문장을 쓰려면 **"58%"라는 초기 수치가 남아 있어야 한다.** 개선 후 수치는 언제든 측정할 수 있지만, 개선 전 수치는 그 시점에 기록하지 않으면 영원히 사라진다.

기록은 세 종류다. 각각 목적이 다르므로 섞지 않는다.

| 종류 | 목적 | 위치 | 주기 |
|---|---|---|---|
| 지표 | 숫자로 된 증거 | DB(자동) + `docs/metrics/` | 자동 + 주 1회 스냅샷 |
| 개발일지 | 무슨 일이 있었나 | `docs/devlog/` | 주 1회 |
| ADR | 왜 그렇게 결정했나 | `docs/adr/` | 결정할 때마다 |

## 1. 지표

### 자동 수집 (DB)

코드가 알아서 남긴다. W1부터 테이블이 존재해야 한다.

**수집 지표** — `COLLECTION_BATCH_LOG`
- 배치 실행 횟수 / 성공률
- 실행당 신규·갱신 공고 수
- **수집 지연**: `RECRUITMENT.posted_at` → `collected_at` 차이. 이게 "공고를 얼마나 빨리 알려주는가"의 지표

**추출 지표** — `EXTRACTION_LOG`
- 시도 수 / 성공 수 / 실패 사유별 분포
- **자동 승인률**: `auto_approved = true` 비율 ← 가장 중요
- **필드 정확도**: `1 - (corrected_field_count / 전체 필드 수)`. 검수에서 몇 개를 고쳤는지로 역산
- 추출 소요 시간 (p50, p95)

**사용 지표** — `CLICK_EVENT` + 접근 로그
- 일별 방문 수 (Nginx 로그 집계로 충분. 별도 분석 도구 불필요)
- 필터 사용 분포 (어떤 직렬·NCS 영역 필터가 많이 쓰이는지)
- 원문 링크 클릭 수 / 공고별 순위
- `.ics` 피드 요청 수 = 사실상의 구독자 수

### 주간 스냅샷

W6부터 Grafana 대시보드에서 수치를 읽어 옮기고, **그 전에는 SQL을 직접 돌려서라도 매주 기록한다.** `docs/metrics/YYYY-Www.md`

> **Grafana가 있어도 주간 스냅샷은 계속 쓴다.** 대시보드는 현재 상태를 보여줄 뿐 "그때 왜 그랬는지"를 남기지 않는다. 자소서에 필요한 건 숫자와 함께 있는 맥락이다. 그리고 외부 지원 기간이 끝나 Grafana를 잃어도 마크다운 기록은 남는다.

```markdown
# 2026-W32 지표

## 수집
- 배치 실행: 168회 / 성공 165회 (98.2%)
- 신규 공고: 23건 / 갱신: 7건
- 평균 수집 지연: 42분 (지난주 51분)

## 추출
- 추출 시도: 30건
- 자동 승인: 19건 (63.3%)  ← 지난주 58.1%
- 검수 대기: 8건 / 추출 실패: 3건
- 필드 정확도: 91.2%
- 실패 사유: HWP 파싱 3건 (전부 구형 바이너리)

## 사용
- 일평균 방문: 34명
- 최다 필터: 전산 + NCS_ONLY (전체의 41%)
- 원문 클릭: 118회
- ics 구독 요청: 9회

## 메모
정보능력 필터 사용률이 예상보다 높음(28%). 필터 UI 상단으로 올릴지 검토.
```

**측정 항목을 도중에 바꾸지 않는다.** 정의가 바뀌면 시계열 비교가 불가능해진다. 새 항목은 추가만 한다.

## 2. 개발일지

`docs/devlog/YYYY-Www.md`. 주 1회, 15분 안에 쓴다. 길게 쓰려 하면 안 쓰게 된다.

```markdown
# 2026-W32 (8/3 ~ 8/9)

## 한 일
- HWP 텍스트 추출기 구현 (#23)
- 추출 실패 시 UNCERTAIN 폴백 처리 (#25)

## 막힌 것과 해결
**구형 HWP 파일에서 hwplib이 예외를 던짐**
- 증상: 10개 중 3개에서 `CompoundFileException`
- 원인: HWP 5.0 이전 포맷. hwplib 미지원 범위
- 조치: 파싱 실패를 예외가 아닌 정상 분기로 처리. UNCERTAIN + 원문 링크 폴백
- 남은 문제: 근본 해결 아님. 실패율 30% 넘으면 LibreOffice 변환 검토 (#31)

## 배운 것
외부 파일 포맷을 다룰 때 "전부 파싱된다"는 가정 자체가 위험. 실패를 정상 경로에
포함시키는 설계가 필요했다.

## 다음 주
- LLM 추출 프롬프트 1차 (#26)
- confidence 산출 로직 (#27)
```

### 공개 발행 (벨로그 등)

개발일지는 벨로그 시리즈로 공개 발행한다. 공개하면 중단하기 어려워져 기록이 유지되고, 포트폴리오에서 "코드 + 사고 과정"을 함께 보여줄 수 있다.

**원본과 공개본을 분리한다.**

| 위치 | 대상 독자 | 성격 |
|---|---|---|
| `docs/devlog/YYYY-Www.md` | 나중의 나 | 날것. 실패·시행착오 포함 |
| 벨로그 | 외부 독자 | 배경 설명을 덧붙인 각색본 |

**🔒 공개 전 필수 확인 — 시크릿·URL 마스킹**

블로그 발행은 **되돌릴 수 없는 유출 경로**다. 검색엔진과 RSS에 즉시 수집되므로, 게시 후 삭제해도 유출된 것으로 간주해야 한다. 발행 전 아래를 매번 확인한다.

- [ ] **인증키·API 키·토큰이 본문·코드블록·스크린샷에 없는가**
  - 공공데이터포털 `serviceKey`, Anthropic API 키, 텔레그램 봇 토큰, DB 비밀번호
  - **특히 스크린샷 주의.** 브라우저 주소창, REST Client 응답 패널, 터미널 히스토리에 키가 그대로 찍힌다
- [ ] **요청 URL을 그대로 붙여넣지 않았는가** — `serviceKey`가 쿼리스트링에 들어간다
- [ ] 서버 IP, 내부 도메인, DB 접속 정보, 관리자 경로가 노출되지 않는가
- [ ] 어드민 화면 스크린샷에 실제 접근 URL이 찍히지 않았는가

**마스킹 표기 규칙** — 지웠다는 사실이 보이게 쓴다. 일부만 남기면 조합으로 복원될 수 있으므로 전체를 치환한다.

```
❌ https://apis.data.go.kr/1051000/recruitment/list?serviceKey=a1B2c3D%2F...
✅ https://apis.data.go.kr/1051000/recruitment/list?serviceKey={SERVICE_KEY}

❌ serviceKey=a1B2c3D4e5...(뒷부분 생략)
✅ serviceKey={발급받은_인증키}
```

스크린샷은 캡처 후 편집 도구로 해당 영역을 **불투명하게 덮는다.** 모자이크나 블러는 복원 가능한 경우가 있다.

> 실수로 발행했다면 **글 수정이 아니라 키 재발급이 먼저다.** 자세한 내용은 `docs/07-security.md` §1 참조.

**"막힌 것과 해결" 섹션이 핵심이다.** 자소서 문제해결 항목은 전부 여기서 나온다. 증상 → 원인 → 조치 → 남은 문제 구조를 지킨다. 특히 "남은 문제"를 솔직히 적어두면 나중에 개선 스토리의 출발점이 된다.

## 3. ADR (Architecture Decision Record)

`docs/adr/NNNN-제목.md`. 구조에 영향을 주는 결정을 내릴 때마다 작성한다.

**작성 대상**: 라이브러리 선택, 스키마 구조 결정, 외부 의존성 추가, 설계 방향 전환
**작성 안 함**: 변수명, 함수 분리, 일상적 리팩터링

```markdown
# ADR-0003: 시험 정보를 공고가 아닌 직렬 단위로 저장

- 상태: 채택
- 날짜: 2026-08-05

## 배경
공고 단위로 시험 정보를 저장하면 스키마가 단순해지고 조인이 줄어든다.

## 문제
실제 공고를 조사한 결과, 같은 공고 안에서 행정직은 NCS만, 전산직은 전공+NCS를
보는 경우가 표본 20건 중 13건이었다. 공고 단위 저장 시 이 차이를 표현할 수 없고,
"NCS만 보는 공고 필터"가 부정확해진다.

## 결정
EXAM_PLAN을 POSITION에 1:1로 연결한다. NCS 영역은 별도 테이블로 분리해
영역 단위 필터링이 조인 쿼리로 가능하게 한다.

## 결과
- 긍정: NCS 영역 필터가 가능해짐. 이 서비스의 차별점이 성립
- 부정: 조회 시 3단 조인 발생 → Redis 캐싱으로 완화
- 부정: 검수 단위가 공고가 아닌 직렬이라 검수 건수가 약 2배

## 대안
- 공고에 JSON 컬럼으로 저장: 필터링 불가로 기각
- NCS 영역을 콤마 문자열로 저장: 인덱싱 불가로 기각
```

**포트폴리오 관점에서 ADR이 특히 강한 이유** — 면접에서 "왜 그렇게 설계했나요"를 반드시 묻는데, ADR이 있으면 그 자리에서 지어내는 대답과 당시 기록을 보여주는 대답의 차이가 난다. 기각된 대안까지 적혀 있으면 더 좋다.

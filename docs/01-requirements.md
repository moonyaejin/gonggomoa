# 요구사항 명세서

## 1. 배경과 목적

공기업 필기시험 준비생은 지원 여부를 판단할 때 두 가지를 본다. **일정**(접수 마감일, 필기시험일)과 **시험 구성**(NCS만 보는지, 전공까지 보는지, NCS는 어떤 영역인지)이다.

일정은 잡알리오에서 확인할 수 있다. 그러나 시험 구성은 각 공고의 첨부파일(HWP/PDF) 본문에만 있어서, 지원자는 공고 하나하나를 열어 PDF를 스크롤해야 한다. 20개 기관을 비교하려면 20번 반복해야 한다.

**이 서비스는 그 정보를 구조화해서 목록·필터·캘린더에서 바로 보이게 한다.**

### 핵심 가치의 우선순위 (W0 검증 후 조정)

실제 공고문 확인 결과, NCS 세부 영역은 별도 참고자료에만 있는 경우가 있어 100% 확보가 불가능하다. 따라서 가치를 다음 순서로 정의한다.

| 순위 | 제공 정보 | 확보 가능성 |
|---|---|---|
| 1 | **필기전형 유무** | 높음 (API `scrnprcdrMthdExpln`) |
| 2 | **시험 유형** (NCS만 / NCS+전공) | 높음 (동일) |
| 3 | **필기시험일** | 중간 (공고문 파싱) |
| 4 | 문항 수·시간·전형 비율 | 중간 (공고문 파싱) |
| 5 | **NCS 세부 영역** | 낮음 (참고자료에만 있는 경우 존재) |

> **1~3번만으로도 기존 서비스에 없는 가치다.** 잡알리오는 필기시험일을 구조화해 보여주지 않는다. "9월 12일에 필기 보는 공기업"을 캘린더에서 한눈에 보는 것 자체가 현재 어디에도 없다. 5번은 확보된 공고에 한해 보너스로 제공한다.

## 2. 범위

- 전산직 / 행정직 2개 직렬
- 공고 수집, 시험 구성 추출, 검수, 조회, 캘린더, 원문 링크
- iCalendar 구독 피드

## 3. 용어

| 용어 | 정의 |
|---|---|
| 기관 | 채용을 진행하는 공공기관·공기업 |
| 공고 | 한 기관이 게시한 하나의 채용 공고 |
| 직렬 | 공고 내 모집 분야 (전산, 행정 등). 시험 구성의 단위 |
| 시험 구성 | 특정 직렬의 필기 전형 내용 (시험 유형 + 과목 + NCS 영역) |
| 시험 유형 | `NCS_ONLY` / `NCS_PLUS_MAJOR` / `MAJOR_ONLY` / `OTHER` |
| NCS 영역 | NCS 직업기초능력 10개 영역 중 출제되는 것 |
| 검수 상태 | 추출 결과의 신뢰 수준 (`AUTO` / `VERIFIED` / `UNCERTAIN`) |

### 사용자 제보 기능을 MVP에서 제외한 근거

공모전 사이트(위비티 등)에는 주최사가 직접 등록하는 폼이 있다. 그러나 그 구조를 이 서비스에 그대로 가져오면 안 된다.

- **공모전은 중앙 집계 데이터가 존재하지 않아** 등록 폼이 유일한 데이터 공급원이다. 반면 공기업 채용공고는 공시 의무가 있어 이미 알리오에 집계되어 있다. 채용 담당자가 우리 사이트에 별도로 등록할 유인이 없다.
- 담당자명·연락처·이메일을 받는 순간 **개인정보 수집이 시작되어** 개인정보처리방침 게시·동의 절차·파기 절차 의무가 발생한다. NFR-5에서 의도적으로 피한 상태가 무너진다.
- 인증 없는 공개 폼 + 파일 업로드는 스팸·악성 파일의 표적이 된다.
- 자유 서술 제보의 검수 부담이 1인 운영 전제를 깨뜨린다.

**v1.1 이후 도입 시 형태**

| 기능 | 수집 항목 | 우선순위 |
|---|---|---|
| 정보 오류 신고 | 공고 ID, 오류 필드, 한 줄 설명 | 높음. LLM 추출 정확도를 사용자가 검증해주는 채널 |
| 누락 공고 제보 | **원문 공고 URL 하나만** | 보통. 포스터·첨부·담당자 정보는 받지 않는다 |

둘 다 개인정보를 수집하지 않는다. 도입 시점은 운영 3개월 후 커버리지 갭이 실제로 확인된 뒤로 한다. 제보 건수 자체가 커버리지 지표가 된다.

### 미확인 정보 표시 정책

**전부 아니면 전무가 아니다.** 시험 유형은 확보했으나 NCS 영역은 못 얻는 경우가 대부분이므로, **필드 단위**로 상태를 표현한다.

| 상태 | 화면 표시 | 조건 |
|---|---|---|
| 확인됨 | 값 그대로 + `검수완료` 배지 | 검수 통과 |
| 미확인 | **"공고문 직접 확인 필요"** + 공고문 링크 | 값이 없거나 미검수 |
| 해당 없음 | "필기전형 없음" | 서류+면접만 시행이 확인된 경우 |

표시 예시

```
한국철도공사 · 2026년 하반기 신입사원 채용
접수  8/18 ~ 8/21        필기  9/12(토)
─────────────────────────────────────
필기 유형   NCS + 전공 + 철도법령          [검수완료]
문항 / 시간  70문항 / 70분                 [검수완료]
NCS 영역    공고문 직접 확인 필요 →         [공고문 보기]
채용직렬    사무영업, 차량, 토목, 전기통신, 운전
            (NCS 분류: 경영회계사무, 기계, 건설, 전기전자, 정보통신)
```

**"공고문 직접 확인 필요"는 실패가 아니라 정직한 상태 표시다.** 추측한 값을 채워 넣는 것보다 낫고, 사용자를 원문으로 안내하는 것 자체가 유용한 동작이다.

### 직렬 표기 정책

NCS 대분류는 기관 고유 직렬명과 일치하지 않는다. 예: 한국철도공사의 `전기통신` 직렬은 전기·신호 설비 직무이나 API에는 `R600020 정보통신`으로 태깅된다. 전산 지원자에게 오인될 수 있다.

**대응**: 필터는 NCS 대분류로 하되, **카드에는 공고문에서 추출한 실제 직렬명을 병기한다.** "이 코드는 실제로 전산이 아니다"를 시스템이 판정하려 들면 기관 수만큼 예외가 생긴다. 판단은 사용자에게 맡기고, 판단에 필요한 정보를 제공하는 데 집중한다.

### 외부 도구 연계를 "내보내기"로 한정한 근거

관심 공고를 스크랩해 노션 등에 모아두려는 수요는 자연스럽다. 그러나 **서버가 사용자 대신 외부 서비스에 데이터를 밀어넣는 방식(OAuth 연동)은 MVP에서 채택하지 않는다.**

- 스크랩은 사용자 식별을 전제하므로 **로그인이 필요해진다.** NFR-5(개인정보 미수집)와 정면으로 충돌한다.
- 노션 OAuth는 **액세스 토큰을 서버에 저장**해야 한다. 개인정보처리방침 게시 의무가 발생하고 토큰 만료 처리·외부 API 장애 대응·사용자별 스키마가 따라온다.
- 1인 운영 · 3개월 배포 목표에서 비용 대비 효과가 낮다.

**대신 "사용자가 자기 도구로 당겨가게 한다."** `.ics` 구독 피드와 동일한 철학이다.

| 방식 | 계정 | 개인정보 | 구현 비용 |
|---|---|---|---|
| OG 메타태그 | 불필요 | 없음 | 매우 낮음 |
| CSV 내보내기 | 불필요 | 없음 | 낮음 |
| 마크다운 복사 | 불필요 | 없음 | 매우 낮음 |
| `.ics` 구독 | 불필요 | 없음 | 낮음 |
| ~~노션 OAuth~~ | 필요 | 토큰 저장 | 높음 |

**OG 메타태그를 필수로 둔 이유** — 공기업 준비생은 스터디 단톡방·오픈채팅에서 공고를 공유한다. 링크가 카드로 표시되면 그 자체가 유입 경로가 되고, 노션에 링크만 붙여넣어도 쓸 만한 목록이 된다. 노션 전용이 아니라 카카오톡·슬랙·디스코드에 모두 적용되므로 투자 대비 효과가 가장 크다.

**v1.1 재검토 조건** — CSV 내보내기 사용량과 클릭 데이터로 스크랩 수요를 확인한 뒤 판단한다. 지금은 추측이며, 수요가 없으면 만들지 않는다.

### 고용유형 수집 범위와 v2 확장 경로

**MVP 수집 대상은 `R1010`(정규직) + `R1070`(채용형 인턴)이다.**

`R1070`을 포함한 이유는 명칭과 달리 사실상 정규직 공채이고 필기를 시행하기 때문이다. 실제 수집 표본에서 근로복지공단 행정직(274명), 한국농어촌공사 7급(122명), 한국토지주택공사 5·6급(262명) 등 대형 공채가 모두 `R1070`으로 태깅되어 있었다. 제외했다면 핵심 공고를 놓쳤을 것이다.

계약직·비정규직·체험형 인턴을 제외한 이유는 **대부분 필기전형이 없기 때문**이다. 필터 없이 조회한 607건은 상당수가 병원 계약직·임시직이었고, 이들이 목록을 채우면 시험 정보 칸이 비어 서비스의 차별점이 희석된다.

**v2 확장은 스키마 변경 없이 가능하다.** `EmploymentType` Enum에 7개 코드가 모두 정의되어 있고 `RECRUITMENT.employment_type` 컬럼도 존재한다. 수집 파라미터 `hireTypeLst`에 코드를 추가하는 것만으로 그날부터 수집된다.

> **v2 확장 시 원칙**: 수집은 넓게, 기본 노출은 좁게. 목록의 기본 필터를 정규직+채용형인턴으로 켜둔 상태로 두고, 사용자가 "전체 보기"를 선택했을 때만 나머지를 노출한다. 그렇지 않으면 필기 정보 없는 공고가 목록을 뒤덮는다.

**`R1030`(무기계약직) 포함 여부는 W1에서 판단한다.** 공무직 채용 중 필기를 시행하는 사례가 있어(대한체육회, 한국공항공사 등) 실호출로 필기 시행 비율을 확인한 뒤 결정한다.

## 6. 제약과 가정

- 공공데이터포털 API 3종(인사혁신처 / 재정경제부 / 행정안전부)의 개발계정 승인은 완료되었다. 주 소스 선정은 W0에서 실제 응답을 확인한 뒤 결정한다.
- **재정경제부 API를 주 소스로 선택할 경우 일일 트래픽이 상세기능당 1,000건이다.** 평상시 운영(시간당 폴링 + 신규 건 상세조회)은 하루 150건 수준이라 여유가 있으나, **초기 백필을 한 번에 실행하면 첫날 한도가 소진된다.** 백필 범위를 최근 2개월로 제한하거나 일자별 분할 실행 로직을 넣는다.
- 인사혁신처 API는 상세기능당 10,000건으로 여유가 있다.
- 구형 HWP 바이너리 포맷은 파싱이 실패할 수 있다. 실패율이 30%를 넘으면 대안(HWP→PDF 변환 후 처리)을 검토한다.
- LLM 추출 정확도 100%는 목표가 아니다. 목표는 **자동 승인률 70% 이상, 승인 건의 필드 정확도 95% 이상**.
- 운영자는 1명이며, 검수에 하루 10분 이상 쓰지 않는 것을 전제로 설계한다.
